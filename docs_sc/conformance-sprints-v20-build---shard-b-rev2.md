## Findings

### Major

- **C-M1 — No write path for the final sprint report; `completed` requires neither conformance nor a final report.** Spec: Lifecycle `completed` row ("Conformance and the final report are recorded") and Sprint Close and Conformance ("The Planner then closes the Sprint with a full sprint report covering the conformance outcome, judgments, issues, mid-Sprint spec edits, and the follow-up list"). On main, `sprint_reports` has exactly three writers — pause (`sprint_domain.py:536`), abort (`sprint_domain.py:365`), conformance (`sprint_close.py:68`) — and no writer for `report_kind='final'` exists anywhere in non-test code. `sc sprint complete` accepts only `--reason/--outcome` (`sprint_cli.py:284-288`), and the transition requires only `terminal_outcome` (`sprint_domain.py:190-193`). The `sprint_close` skill instructs "commit the final or abort report before the lifecycle transition" against a command that does not exist. A Sprint can reach `completed` with zero conformance and zero final report; the spec's terminal-state definition is both unimplementable and unenforced. **Verdict class: unimplemented.**
- **C-M2 — FnB cannot disposition conformance follow-ups.** Spec: "recorded as follow-ups for FnB review… The Sprint ships; the FnB dispositions the follow-ups." There is no `UPDATE sprint_followups` path anywhere in the engine — no API endpoint, no CLI verb. The schema anticipates disposition (0150's `accepted/resolved/dismissed` + resolution CHECK, and an immutability trigger that carves out disposition columns), but nothing can move a follow-up out of `pending`; the report packet reads `pending`/`accepted` as unresolved forever. **Verdict class: unimplemented.**

### Medium

- **C-m1 — Post-approval head move wedges the unit in `merge_ready` (deviated-silently).** After an approved review, if the PR head moves, `authorize_merge` rejects the stale approval (`sprint_review_loop.py:247-251`), but `request_review` refuses `merge_ready` (`:104-107`) and `record_review` requires `in_review` (`:175-178`). No re-review or un-wedge path exists; the merge grant's staleness semantics ("waits for the watcher's next green wake") cover regressed checks at the same head only. Verified empirically against the test fixture; no test covers the scenario.
- **C-m2 — Same-state head movement is invisible to the transition log (deviated-silently).** `observe_in_transaction` dedupes on `normalized_state` only (`sprint_pr_watcher.py:405-407`): green→green at a new head records no transition, fires no wake, and leaves `observed_head_sha` stale. `request_review`/`record_review` staleness checks compare against this log, so a review can be requested and approved against a superseded head — the merge gate catches it later, and then C-m1 wedges the unit.
- **C-m3 — Wedged-but-alive worker never escalates (partially deviated-intentionally).** Post-nudge Planner escalation requires `not snapshot.supporting` (`sprint_liveness.py:726-733`), and `process.present` is stamped `observed_at=now` on every evaluation (`:450-460`), so a live-but-hung harness process defers escalation forever (test asserts no escalation even at +40 min). Decision #42 (ratified) blesses suppression "while it positively shows healthy work" — but bare process presence is not positive evidence of healthy work, so the mechanism is broader than the ratification. The spec's policy text is unconditional ("continued silence beyond a further ten-minute window creates one active Planner escalation"); the carve-out needs either a ceiling in code or a spec write-back.
- **C-m4 — Git commits are not consumed as strong liveness evidence (deviated-silently).** The spec's strong-evidence list includes "Git commits and registered PR transitions". Registered PR transitions are consumed (`sprint_liveness.py:353-370`); git commits are not — only a non-commit-specific `worktree.observed` supporting signal, refreshed at run completion (`:415-436`; `conversation_git_targets.py:178-188`).
- **C-m5 — Terminally-failed wakes are stranded across resume, and invisible in reconciliation (deviated-silently).** `record_wake_failure` sets the wake `failed` (`sprint_domain.py:447-458`); nothing ever resets it (`claim_next` takes only `pending`/expired-`delivering`, `sprint_message_delivery.py:487-489`); resume evidence lists only pending/delivering wakes (`sprint_domain.py:847-854`). The canonical auto-pause scenario (`wake_delivery_exhausted`) resumes with the very assignment that caused the pause undelivered and unsurfaced — recovery depends on an unrelated future wake or a liveness nudge. No test exercises resume after a `wake_delivery_exhausted` pause.
- **C-m6 — Bound-spec edit guard is resume-granular only (deviated-silently).** Spec: a bound governing spec "may be edited only by its owning Planner or the FnB; the system records any other write as drift evidence and notifies the Planner the same way (a policy guard with detection, not a write lock)". On main, `patch_document` checks only `frozen` (`server.py:1109-1120`) — any shell may edit a bound spec mid-Sprint with no write-time detection, no actor recorded, no notification; drift is computed only at resume by sha compare (`sprint_domain.py:771-786`), which is blind to edit-then-revert and cannot name the writer. An armed Sprint that never pauses never detects mid-Sprint edits at all (they surface only as hash drift in the close packet).
- **C-m7 — The evidence packet's `pause_and_recovery` section omits resume/reconciliation (deviated-silently).** The section filters events on markers `pause/resume/recover/interrupt/drift` (`sprint_close.py:134-141`), but resume emits `lifecycle.reconciled` and `lifecycle.armed` (`sprint_domain.py:288-323`) — the single richest recovery evidence (reconciliation payload incl. spec drift and anomalies) matches no marker and never appears in the section or in `anomalies`.
- **C-m8 — "FnB drives close" positive path is untested; the acceptance manifest overclaims (deviated-silently).** The manifest maps "FnB authority can compile evidence when the Planner is unavailable" (`tests/fixtures/sprint_v2_acceptance.json:80-82`) to `test_only_planner_or_admin_compiles_and_participants_read_timeline`, whose denied caller is a dev-flavored shell — the admin branch of `_require_close_authority` (`sprint_close.py:410-414`) is never positively exercised, and FnB `complete` is untested. The mechanism exists (R4/banked u9-L2 below); the evidence does not.
- **C-m9 — Report-only/no-code work units cannot complete (unimplemented surface).** Spec: "A work unit explicitly planned as report-only or no-code may complete with a durable result rather than a PR." `SprintWorkUnitStore.complete` (`sprint_domain.py:1397`) implements it but has zero production callers — no endpoint, no CLI verb; the `cancelled` disposition is likewise unwritable. In a live Sprint the only route to `completed` is merge observation, so a Sprint containing a no-code unit can never fully terminate (unresolved units surface in the packet but nothing can resolve them).

## Candidate spec clarifications (spec silent, implementation chose)

1. **Replacement-Planner authority on close-out (banked REV1 u9-L2 — confirmed):** only the originating Planner or FnB can compile/complete/abort; a booted replacement Planner has no close-out authority. Spec should state this.
2. **Head-change-after-approval recovery:** whether a moved head re-enters review from `merge_ready` or requires Planner intervention (C-m1).
3. **Supporting-evidence deferral of post-nudge escalation:** decision #42 ratified the policy; the spec's unconditional escalation text should carry the carve-out — and define what "positively shows healthy work" means (C-m3).
4. **"Coalesces behind the active turn"** is implemented as coalescing into an existing pending wake; there is no in-flight-turn detection.
5. **"Real browser conversations" (Stage 10) vs DB-enqueued prompts** — R6 redefined the proof shell-driven; reconcile the gate text with the architecture.
6. **Who executes the merge:** the engine has no merge-execution path (`GitHubPullRequestReader` is read-only); "merge under the grant" means the Developer shell merges externally and the watcher observes. R6's "engine production merge path" does not exist — vocabulary never reconciled.
7. **Conformance during pause:** `record_conformance` requires `armed`; spec is silent on whether a paused Sprint may record conformance.
8. **Close-out reviewer onboarding:** participants are fixed at declaration; a Sprint declared without a reviewer can never record conformance. Spec should say the conformance reviewer must be declared up front (or demand an add-participant path).
9. **Completion gate:** the engine allows `completed` with non-terminal units (surfaced as unresolved in the packet); spec should say whether this is deliberate.
10. **Merge-grant binding time:** mandatory at declare via the surface; schema permits disabled. State whether no-grant Sprints are in scope.
11. **FnB dispatch/monitor:** exact originating Planner only, no admin override — if the Planner shell is down, nobody can dispatch/monitor. State whether FnB may.
12. **Follow-up `accepted` disposition** has no defined semantics (packet treats it as unresolved, like `pending`); severity vocabulary is conventional, not enforced.
